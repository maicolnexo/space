Protocolos de seguridad

Elegí un ámbito con los botones inferiores, completá el checklist (se guarda en este navegador) y usá los accesos rápidos a la documentación oficial.

Docs · Security Rules Simulador de reglas Firebase Authentication App Check Android · Buenas prácticas

Principios (orden de impacto)

  • Mínimo privilegio: cada usuario solo lee o escribe lo que necesita (por rol, sede u operador).
  • Confiar en el backend: Firebase Security Rules y Cloud Functions validan datos; el HTML/JS de la web es visible para cualquiera.
  • Cifrado en tránsito: HTTPS obligatorio (Firebase y hosting ya lo usan); no mezclar contenido HTTP en páginas HTTPS.
  • Secretos fuera del cliente: claves de APIs, saltos de cifrado sensibles y lógica crítica deben vivir en Cloud Functions o en entorno servidor, no en firebase-config.js ni en strings del APK.
Importante. La API key de Firebase en la web es pública por diseño; la seguridad depende de reglas de Firestore/Storage, dominios autorizados en Authentication y App Check si lo activan.

Firebase y Firestore

Reglas

  • Sustituir reglas abiertas (allow read, write: if true) por condiciones con request.auth, roles en custom claims o documentos de perfil.
  • Limitar rutas: por ejemplo que un operador solo escriba bajo su sede o su código Lug…, según su modelo de datos.
  • Validar forma de los datos con request.resource.data (campos obligatorios, tipos, rangos).
  • Probar reglas con el simulador de la consola y, si pueden, con la Rules Unit Testing suite.

Authentication

  • Mantener lista de dominios autorizados solo con sus sitios reales (Firebase Console → Authentication → Settings).
  • Para cuentas administrativas: verificación en dos pasos en Google y políticas de contraseña si usan email/contraseña.
  • Evaluar Firebase App Check (Play Integrity / reCAPTCHA) para reducir abuso de APIs desde apps y bots.

Storage y datos sensibles

  • Reglas de Storage alineadas con Firestore (misma idea de identidad y rutas).
  • Los datos “encriptados” en el cliente (p. ej. cierres) no sustituyen reglas: quien tenga el secreto en el APK o en la web puede descifrar; para secreto real hace falta servidor o gestión de claves.

Sitio web (HTML estático)

  • Hosting: solo HTTPS; si usan CDN (Firebase Hosting, Cloudflare), activar “Always HTTPS” y redirecciones 301.
  • Cabeceras (según el proveedor): Content-Security-Policy restrictiva, X-Content-Type-Options: nosniff, Referrer-Policy. Firebase Hosting permite configurar cabeceras en firebase.json.
  • No guardar tokens o datos sensibles en localStorage sin criterio; preferir sesión de Firebase Auth gestionada por el SDK.
  • Revisar que enlaces externos usen rel="noopener noreferrer" cuando abran en nueva pestaña.

App Android

  • Firma y distribución: Play App Signing; subir solo AAB firmado; no commitear keystores ni contraseñas al repositorio.
  • Ofuscación: R8/ProGuard activado en release para dificultar ingeniería inversa (no es cifrado absoluto).
  • Network Security Config: solo confiar en certificados válidos; valorar certificate pinning solo si tienen equipo para mantenerlo.
  • Datos locales: EncryptedSharedPreferences / Android Keystore para tokens si deben persistir.
  • Actualizaciones: mantener dependencias (Firebase BOM, OkHttp, etc.) y revisar avisos de Play Console.

Prioridades sugeridas

Prioridad Acción
Alta Endurecer reglas de Firestore y Storage; dominios autorizados correctos; revisar índices y consultas expuestas.
Alta Definir roles (claims o colección users) y reflejarlos en las reglas.
Media Activar App Check; MFA para administradores; cabeceras HTTP en hosting.
Media Mover lógica sensible a Cloud Functions (validaciones, sumarios, reportes críticos).
Continua Auditoría periódica de la consola Firebase, backups/exportaciones según política de retención, rotación de cuentas de servicio.

Responsables y revisión

Designar una persona o rol que revise trimestralmente: reglas desplegadas, usuarios con acceso a la consola, listado de apps OAuth y dependencias del proyecto Android. Tras cada incidente o cambio grande en datos, actualizar esta página o un documento interno con la fecha y el alcance del cambio.
